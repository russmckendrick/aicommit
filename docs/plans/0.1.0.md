# Plan: aicommit 0.1.0

Status: draft, not started.

0.1.0 is the first release after the 0.0.x series that changes how `aic` *feels* rather than adding another subcommand. It has three themes:

1. **An interactive terminal UI** for the commit, split, review, and history flows, built with `ratatui`.
2. **Hunk-level split commits**, so one file can contribute to more than one commit.
3. **Streaming and machine-readable output**, so people see messages as they are written and scripts or coding agents can call `aic` reliably.
4. **A polish bar that impresses people.** The bar is that someone watching a 20-second demo asks "what is that?" This is a release requirement, not a nice-to-have. See [Design bar](#design-bar).

Everything stays in the terminal. The prompt-driven flow (`inquire`), `--yes`, `--dry-run`, hooks, and non-TTY use keep working exactly as they do today.

## Why not a GUI (GPUI)

GPUI was considered and rejected for this release:

- `aic` runs inside the Git workflow: after `git add -p`, from `prepare-commit-msg`, over SSH, and in scripts. A GPU window adds friction to the happy path and cannot work in the headless cases.
- GPUI is pre-1.0 and evolves with Zed's needs. The API churn is a poor fit for a project that gets attention in bursts.
- Distribution is currently a single static binary via Homebrew, WinGet, and GitHub Releases. A GPU app brings graphics-backend requirements, larger binaries, and signing/notarisation.

A desktop "AI Git client" could be a separate project later. It is out of scope here.

## Where the code is today

The pieces this plan changes:

- `src/commands/commit/` drives the commit flow and calls `ui::select`, `ui::confirm`, and `ui::editor` inline. Flow logic and terminal I/O are interleaved, so a second frontend cannot reuse them.
- `src/commands/commit/split/` splits by **file**. Execution does `git::clear_index()` and then `git::add_files()` for each group (`split/drafts.rs`), which is why `split/flow.rs` refuses to split when any file is partially staged.
- `src/ai/mod.rs` exposes `AiEngine::generate_commit_message(&[ChatMessage]) -> Result<String>`. The name is historical: review, PR, split, and guidance all use it too. Nothing streams.
- `src/generator/` already reports `GenerationProgress` through a callback. That is a good seam to extend.
- `src/ui.rs` is the single styling layer for the prompt flow. It stays, but it is no longer the only frontend.

## Phase 0: Foundations

This phase has no user-visible change except `--json`/`--quiet`. Everything later depends on it.

### 0.1 Extract a frontend-agnostic commit session

Add `src/session/`, a state machine for a commit session that does no terminal I/O:

- **State:** staged files and hunks, current message, split groups, generation status, and provider/model metadata.
- **Actions:** `Generate`, `Regenerate { context }`, `EditMessage(String)`, `ProposeSplit`, `MoveHunk { hunk, to_group }`, `Commit`, `Abort`.
- **Events:** progress, streamed tokens, errors, and a "committed" result.

Then port `commands::commit::run` so the existing `inquire` flow becomes a thin frontend over the session, with behaviour unchanged. The existing CLI tests in `tests/cli.rs` are the safety net for this port. Do review, history, and PR the same way only when the TUI needs them, not up front.

### 0.2 Rename and extend the engine trait

In `src/ai/mod.rs`:

- Rename `generate_commit_message` to `complete`, as a mechanical rename across all call sites.
- Add `stream(&self, messages) -> Result<BoxStream<'_, Result<String>>>` with a default implementation that calls `complete` and yields once. Providers then opt in one at a time.
- Implement real streaming for:
  - `openai_compat.rs`: SSE (`stream: true`), via `reqwest`'s `stream` feature and `futures`.
  - `anthropic.rs`: Messages API SSE (`content_block_delta` events).
  - `command/`: stream stdout line by line where the CLI streams. If a CLI only prints at exit, keep the default.
- Chunked generation (the summary passes) stays non-streaming. Only the final synthesis call streams.

Keep these providers behind `AiEngine` as `AGENTS.md` requires. `wiremock` can serve SSE bodies for tests.

### 0.3 Structured diff model

Add a `src/git/diff.rs` module (Git process calls stay in `src/git/`):

- Parse `git diff --cached` into `FileDiff { path, old_path, status, hunks: Vec<Hunk> }`.
- Give each hunk a stable `HunkId` (`path#n`).
- Build a patch from any subset of hunks.
- Treat binary files, renames, mode changes, and new or deleted files as atomic: one hunk, never split.

### 0.4 `--json` and `--quiet`

These come from the roadmap.

- `--quiet` prints only the final message to stdout.
- `--json` prints a stable, versioned object, for example `{ "schema": 1, "message": ..., "files": [...], "provider": ..., "model": ... }`.
- Apply both to `aic`, `aic review`, and `aic pr`. Both imply non-interactive mode and never commit unless `--yes` is also passed.
- Document the schema in a new `docs/automation.md`, so coding agents (Claude Code, Codex, and others) can treat `aic` as a tool.

## Phase 1: Hunk-level split commits

### Prompt contract

- Update `prompts/split-system.md` so groups list **hunk IDs** instead of file paths: `"hunks": ["src/ui.rs#1", "src/ui.rs#3"]`.
- The diff sent to the model gets a short marker comment above each hunk carrying its ID.
- Validation: every hunk appears exactly once, and IDs are never invented. This is the same rule the parser in `generator/split_plan.rs` applies to files today.
- Fallback: if the model returns file paths, expand each file to all of its hunks. Older or custom prompts keep working.

### Execution without touching the working tree

Replace `clear_index` + `add_files` with:

1. Snapshot the index with `git write-tree` and keep the tree ID for rollback.
2. Reset the index to `HEAD`.
3. For each group, run `git apply --cached` on that group's patch, then commit.
4. On any failure, restore the snapshot with `git read-tree <tree>` and report which groups were committed.

The working tree is never modified. This removes the "partially staged files" restriction in `split/flow.rs`.

### Tests

- Fixture repos built with `tempfile`, using `cwd_test_lock` like the existing tests.
- Cover: one file split across two commits, a rename plus an edit, a binary file, a new file, and rollback after an injected `git commit` failure.

## Phase 2: Terminal UI

New crate dependencies: `ratatui`, `crossterm`, and `tui-textarea` for the message editor. Pin current versions when the work starts.

### Entry and rollout

- Opt in for 0.1.0 with `aic --tui`, `AIC_TUI=true`, or `aic config set AIC_TUI=true`.
- Never used when stdout is not a TTY, or with `--yes`, `--dry-run`, `--json`, `--quiet`, or the hook path.
- Make it the default in a later release once it has had real use. That decision belongs to that release, not this one.

### Screens

| Screen | Contents | Key actions |
|--------|----------|-------------|
| Commit | File/hunk tree (left), diff (right), message editor (bottom) with streamed output | space stage/unstage, `g` generate, `r` regenerate with context, `e` edit, `c` commit, `s` split, `?` help |
| Split | Groups as columns, each listing its hunks, with a per-group message | move hunk left/right, new or merge group, regenerate one group's message, commit all |
| Review | Findings grouped by severity (left), diff scrolled to the finding (right) | enter jump to location, `n`/`p` next/previous |
| History | Replaces `commands/history/interactive.rs` | filter by kind, copy, open |

### Structure

- `src/tui/` holds `app.rs` (event loop), `screens/`, and `widgets/` (diff view, hunk tree, message editor).
- The TUI drives the same `session` as the prompt frontend. Neither frontend contains Git or AI logic.
- Theme colours come from `src/map/theme.rs` where possible, so `aic map` and the TUI look like one product.
- Snapshot-test screens with `ratatui`'s `TestBackend` and `insta`.

`setup`, `config`, and `models` stay on `inquire`. They are short linear prompts and don't need a TUI.

## Design bar

Modern TUIs (lazygit, Helix, Posting, Yazi) set what people now expect from a terminal app. 0.1.0 should sit in that company. Each item below is a check before release.

- Each column is a proposed commit, with the model's title, its reason, and a draft message.
- One file can feed several commits. `src/ui.rs` appears in two groups, and the UI says so ("same file").
- Moving a hunk previews its diff in the panel below. Only the affected groups' messages are regenerated.

Rules these mockups set for every other screen:

- One accent colour (blue) marks focus and selection. Green, amber, and red only ever mean added, partial, and removed.
- Panels get rounded borders and padding. The commit message is the brightest text on screen.
- The header row (screen, branch, model, cost) and the key-hint footer look the same on every screen.

### Look

- **One visual identity.** Define a small token set (background, surface, border, muted, accent, plus success/warn/error) in `src/tui/theme.rs`. Derive it from the `aic map` themes so screenshots, SVG maps, and the TUI all match. Ship at least `github-dark`, `github-light`, `dracula`, and `solarized`.
- **Detect light/dark automatically** by querying the terminal background (OSC 11), with `AIC_THEME` to override.
- **Use truecolor when the terminal supports it.** Fall back cleanly to 256 colours and then 16, without breaking contrast. Test in Terminal.app, iTerm2, Ghostty, WezTerm, Windows Terminal, and tmux.
- **Use rounded borders, generous padding, and one accent colour.** Selection, focus, and the primary action should never compete for attention.
- **Highlight diff syntax** with `syntect` (or `tree-sitter-highlight`) on top of add/remove backgrounds, and show intra-line word diffs. This is the single biggest visual upgrade over `git diff`.
- **Nerd Font icons are opt-in** (`AIC_ICONS=nerd`). The default glyphs stay Unicode-safe, using the existing `◇ • ⠹` vocabulary from `ui.rs`.

### Motion

The aim is motion that feels alive without being slow. Nothing should block input.

- **Stream the message token by token** with a soft cursor. This is the hero moment of the demo.
- **Show progress as a slim animated bar with the real stage**, taken from `GenerationProgress`: "Summarising chunk 2/4", then "Synthesising".
- **Animate split groups:** when the model proposes groups, hunks slide into their columns over about 150 ms.
- **Confirm commits with a brief success state:** short SHA, branch, and a single tick that fades. No confetti.
- **Keep the frame budget:** redraw only on events, at no more than 60 fps, and with no visible flicker over SSH.

### Feel

- **Ease the first run.** If no provider is configured, `aic --tui` opens a guided setup panel instead of failing with an error.
- **Command palette** (`ctrl-k` or `:`) to find any action, with its shortcut shown next to it.
- **Context-aware key hint bar** at the bottom, plus a `?` overlay that lists every binding.
- **Support the mouse:** click to stage, scroll the diff, drag hunks between split groups.
- **Responsive layout:** side-by-side panes at 120+ columns, stacked panes below 100 columns, and a clear "terminal too small" state below the minimum.
- **Never block the UI.** Generation runs in the background. `esc` cancels a request in flight; `g` restarts it.
- **Write errors in plain English**, with a suggested fix: "Anthropic returned 401: check `AIC_API_KEY` or run `aic setup`". Never dump a stack trace into the UI.

### Showcase

- **Record demo tapes with `vhs`** (`docs/tapes/*.tape`) for commit, split, and review, and render them to GIF/MP4 in CI so the README demo never goes stale.
- **Put a hero GIF at the top of `README.md`.** Show the split screen in action within the first five seconds.
- **Add a screenshot gallery to `docs/tui.md`**, one image per theme.

### How "wow" gets checked

- Before release, watch two or three people who have never seen `aic` try it, without explaining anything. Note every hesitation.
- Snapshot-test each screen at 80, 120, and 200 columns, in both light and dark themes.
- Keep a polish backlog (`docs/plans/0.1.0-polish.md`) and give it time in every phase, not just at the end.

## Phase 3: Smarter messages

- **Repo style inference:** sample the last N commit subjects and detect conventional vs free-form, gitmoji or not, the scope vocabulary, and case/tense. Feed a compact summary into `prompts/commit-system.md` and cache it per repo. This replaces the roadmap's "commitlint-style config inference"; read a real commitlint config when one is present.
- **Config profiles** (roadmap): `~/.aicommit.d/<name>.toml`, chosen with `--profile` or matched against the remote URL.
- **Token and cost estimate:** show it in the session metadata row, and in the TUI header.

## Suggested PR sequence

Each step can ship on its own:

1. Rename `generate_commit_message` to `complete` (mechanical).
2. Add the `stream` default method, then OpenAI-compatible and Anthropic streaming, shown in the existing spinner flow.
3. Add `--quiet`, `--json`, and `docs/automation.md`.
4. Add the `git/diff.rs` hunk model and patch builder, with tests.
5. Execute splits through an index snapshot plus `git apply --cached`, still grouping by file. This lifts the partial-staging restriction.
6. Move the split prompt and parser to hunk IDs.
7. Extract `session/` and port the prompt frontend.
8. TUI theme tokens, syntax-highlighted diff widget, and `vhs` tape harness. The look is settled before any screen is built.
9. TUI skeleton plus the Commit screen behind `--tui`, with streaming, hint bar, and palette.
10. TUI Split screen with mouse drag and animations.
11. TUI Review and History screens.
12. First-run setup panel and the responsive layout pass.
13. Repo style inference.
14. Config profiles and the cost estimate.
15. Polish pass, hallway testing, hero GIF, docs, and `docs/releases/0.1.0.md`.

Steps 1–6 improve the existing CLI even if the TUI slips.

## Open questions

- In the TUI, edit messages inline (`tui-textarea`) only, or also offer `$EDITOR` behind `E`?
- Should the TUI become the default in 0.2.0, or stay opt-in?
- Is it worth adding an `aic mcp` server mode, or is a stable `--json` enough for agent use?
- Is the version 0.1.0, or is this the release that becomes 1.0?
- Given the polish bar, should the TUI be on by default from 0.1.0 instead of opt-in? That makes a stronger first impression but carries more risk. Opt-in plus a hero GIF is the safer launch.
